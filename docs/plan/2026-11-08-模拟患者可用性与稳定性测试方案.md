# 模拟患者可用性与稳定性测试方案（2026-11-08）

> 面向「老年人就医预问诊与老年综合评估系统」二期。
> 本方案配套 **100 名模拟患者测试数据集**（`docs/structured/simulated-patients/`），
> 数据已生成并通过自检，**本轮只建数据与方案，不执行测试**。

---

## 1. 测试目标与范围

### 1.1 目标

| 目标 | 说明 |
| --- | --- |
| **可用性** | 医护端与老人端主流程能否**跑通**、结果能否**看懂**，100 名模拟患者走完真实交互不卡壳、不中断 |
| **准确性** | 从仿真对话里抽症状、匹配病种、给提醒、生成报告——结果与真值的一致程度 |
| **稳定性** | 并发、长时间运行、异常输入下不崩溃、不泄漏、不错乱 |
| **合规性** | 红线是否被守住：AI 不下诊断、术语规范、越权被拒、留痕完整 |

### 1.2 在范围内

- 医护端：评估任务、患者管理、预问诊、量表施测、匹配与复核、报告、提醒、随访、质控
- 老人端：登录、建档、预问诊对话、量表作答、报告查看
- 后端 API 全链路（见 §4.1 的接口清单）

### 1.3 不在范围内（避免与线 A 抢活）

- 预问诊**采集逻辑**、题库内容、判读引擎内部实现——属线 A，本方案只做**黑盒验证**
- 大模型效果评测（准确率/幻觉率）——需要另立专项与标注集
- 医疗专业结论的临床正确性——本方案只验证「系统给出的候选与证据是否自洽、是否可复核」

## 3. 测试数据集设计（100 名模拟患者）

### 3.1 分层与考察点

| 分层 | 人数 | 构造方式 | 考察什么 |
| --- | --- | --- | --- |
| `clear` 主诉明确 | 60 | 2~4 个核心症状 + 1~3 个次要症状 | 主链路顺畅、Top-1 命中、报告完整 |
| `vague` 信息不足 | 15 | 只报 1~2 个非特异症状 | Top-3 内命中、**应触发追问**而非硬答 |
| `red_flag` 高危红旗 | 10 | `immediate` 病种 + 晕厥/胸痛/意识改变 | 「立即就医」提醒必须触发 + 强制人工复核 |
| `comorbid` 共病 | 10 | 2 个病种同时存在 | 多个候选 + 冲突标记 + 交医护复核 |
| `special` 特殊交互 | 5 | 耳背 / 方言 / 认知障碍 / 拒答 | 听不懂就追问，**不得臆断**；人工兜底可用 |

### 3.2 覆盖度（生成器实测）

| 维度 | 覆盖 |
| --- | --- |
| 病种 | **28 / 28 全覆盖**，每种 ≥2 例（真值取自 `docs/structured/disease-library/diseases.json`） |
| 症状词表 | **113 / 113 全覆盖**（真值取自 `symptoms.json`） |
| 风险等级 | immediate 21 / urgent 48 / elective 31 |
| 对话规模 | 3215 轮，平均 32.1 轮/人 |
| 量表作答 | 100 组，按真值病种推导典型作答模式 |

### 3.3 每人包含四类信息

| 信息 | 位置 | 说明 |
| --- | --- | --- |
| **患者基本信息** | `patients.json → basic_info` | 性别/年龄/住址（脱敏）/联系方式（保留测试号段）/婚姻/文化程度/居住安排/方言/听力/视力/认知/手部功能/照护者 |
| **医患仿真对话** | `dialogues.jsonl` | 按 15 个采集意图分段（identify → chief_complaint → symptom_detail → onset → negative → associated → red_flag → history → medication → allergy → family_history → lifestyle → fall_history → functional → preference），含填充词、重复、自我更正、听不清、答非所问五类噪声 |
| **患者疾病表征** | `patients.json → disease_presentation` | 主诉（部位/性质/伴随/起病）+ 阳性症状清单（编码/严重度/病程/起病/规律/缓解因素/患者原话）+ **阴性症状**（供匹配引擎给「缺失关键症状」证据） |
| **患者实际疾病** | `patients.json → expected_disease` | 真值病种编码/名称/风险等级 + 应命中的核心症状 + 干扰病种 + Top-1/Top-3 期望 + 是否须人工复核 |

> ⚠️ `expected_disease` 是**测试断言基准**，不是系统输出。系统侧禁止输出诊断结论
> （见 `AGENT.md` 领域红线 2），测试要校验的正是「系统给的是候选与证据、真值由测试持有」。

### 3.4 数据生成与自检

```bash
python tools/gen_simulated_patients.py          # 重新生成（确定性，种子 20261108）
python tools/check_simulated_patients.py        # 自检，6 类校验
```

自检里最关键的一项是**可抽取性**：对话里每一句被标注的症状，都必须能被后端
`services/dialogue.py::extract_symptoms()` 的匹配规则（标准词 + 同义词 子串匹配）抽出来；
标注为「抽不中」的方言/识别噪声句必须抽不出来——这正是 `special` 组要验证的行为。

## 4. 测试场景与用例

### 4.1 端到端主流程（E2E，100 人 × 全流程）

| # | 步骤 | 接口 | 断言 |
| --- | --- | --- | --- |
| 1 | 登录取令牌 | `POST /auth/login` | 200；角色正确（老人/医护/管理员） |
| 2 | 建档 | `POST /patients` | 201；档案字段落库且与数据集一致 |
| 3 | 知情同意 | `POST /patients/{id}/consent` | 201；`ai_involved` 标记正确 |
| 4 | 预问诊建会话 | `POST /dialogue/sessions` | 201；会话可查 |
| 5 | **逐轮投喂仿真对话** | `POST /dialogue/sessions/{id}/messages` | 每轮 200；SSE 正常收尾；**无 5xx** |
| 6 | 抽取结果 | `GET /dialogue/sessions/{id}/profile` | 症状集与期望一致（见 §5.2） |
| 7 | 写入预问诊摘要 | `PUT /patients/{id}/preconsult` | 200；主诉/病史落库 |
| 8 | 建评估会话 | `POST /assessments` | 201；带题库版本 |
| 9 | 提交量表作答 | `POST /assessments/{sid}/answers` | 每题 200/422 语义正确（越界必须 422） |
| 10 | 结束评估 | `POST /assessments/{sid}/finish` | 200；判读结果与标准一致 |
| 11 | 触发匹配 | `POST /matching/run` | 201；返回 Top-3 候选 + 匹配度 + 参考概率 + 证据 |
| 12 | AI 复核 | `POST /matching/runs/{id}/ai-review` | 200；只给建议/追问/解释，**不下诊断结论** |
| 13 | 生成报告 | `POST /reports` → `GET /reports/{id}` → `GET /reports/{id}/export` | 200；报告含免责声明与「待医护评审」标记 |
| 14 | 提醒 | `GET /alerts` → `POST /alerts/{id}/handle` | 风险等级正确（见 §5.3） |
| 15 | 复核裁决 | `POST /assessments/{sid}/review` | 200；留痕可查 |
| 16 | 随访/周期评估 | `POST /followups` → `POST /periodic/run` | 异步任务最终状态正确 |
| 17 | 质控指标 | `GET /admin/quality-metrics` | 指标可算、不为 null |
| 18 | 审计留痕 | `GET /admin/audit-logs` | 关键操作均有留痕 |

### 4.2 可用性用例（按分层 × 关键步骤）

| 用例 | 输入 | 期望 |
| --- | --- | --- |
| U-01 清晰主诉 | `clear` 60 人 | 全流程无人工干预完成；报告可读 |
| U-02 信息不足 | `vague` 15 人 | 系统**主动追问**缺失信息；不得凭 1 个症状硬给 Top-1 |
| U-03 红旗识别 | `red_flag` 10 人 | `immediate` 100% 触发「立即就医」；报告顶部红标 |
| U-04 共病冲突 | `comorbid` 10 人 | 给出 ≥2 个候选并标记冲突，交人工裁决 |
| U-05 沟通受限 | `special` 5 人 | 抽不中的那句触发追问；不得臆断；人工兜底入口可达 |
| U-06 老人端自助 | 任取 20 人走老人端 | 适老化流程可独立完成（不依赖医护代填） |
| U-07 断点续做 | 中断后重进 | 评估会话可恢复，数据不丢 |
| U-08 重复提交 | 同一作答重复提交 | 幂等，不产生重复评估 |

### 4.3 稳定性用例

| 用例 | 方法 | 关注 |
| --- | --- | --- |
| S-01 串行基线 | 100 人全流程串行 | 各步 P50/P95/P99 |
| S-02 并发梯度 | 10 / 30 / 50 并发各跑 3 轮 | 错误率、P95 拐点、连接池耗尽 |
| S-03 长稳 | 2 小时持续 1 req/s 混合流量 | 内存增长、句柄泄漏、Celery 队列堆积 |
| S-04 异常输入 | 空对话、10 万字超长、非法枚举、缺字段、超大作答集 | 422 而非 5xx；不崩溃 |
| S-05 依赖抖动 | 断 Redis / 重启 Celery / 大模型超时 | 降级路径可用，任务可重试 |
| S-06 大数据量 | 一次匹配 100 人批量 | 批处理耗时与内存 |
| S-07 越权 | 老人令牌访问医护端；A 访问 B 患者 | 一律 401/403，且有审计 |

### 4.4 合规与红线用例

| 用例 | 校验点 |
| --- | --- |
| C-01 术语 | 全链路输出零命中「确诊概率 / 患病概率」 |
| C-02 不下诊断 | AI 复核与报告不含诊断结论、无加减停药建议 |
| C-03 免责 | 匹配结果与报告均带「仅供参考，不构成诊断」 |
| C-04 留痕 | 匹配/复核/报告/提醒都有版本与操作人留痕 |
| C-05 隐私 | 日志与报告不含身份证全号；导出需授权 |
| C-06 待评审 | 全库结论仍带「待医护评审」提示（未评审不得自动转正式） |

## 5. 指标与判据（量化）

### 5.1 可用性

| 指标 | 目标 | 判据 |
| --- | --- | --- |
| 主流程任务成功率 | ≥ 99% | 100 人 × 18 步，成功率 ≥ 99% |
| 步骤级 5xx 率 | 0 | 任一步出现 5xx 即为阻断缺陷 |
| 步骤 4（对话）P95 时延 | ≤ 3s | 不含大模型排队 |
| 步骤 11（匹配）P95 时延 | ≤ 5s | 162 节点规模 |
| 步骤 13（报告导出）P95 时延 | ≤ 10s | 含 Word/PDF |
| 错误信息可读性 | 100% | 4xx 必须给出可执行的中文提示 |

### 5.2 抽取准确性（对话 → 症状）

| 指标 | 目标 |
| --- | --- |
| `clear` 组症状召回率 | 100%（数据集保证句子可抽） |
| 全组症状召回率 | ≥ 90% |
| 症状精确率 | ≥ 85% |
| 阴性症状识别率 | ≥ 80%（能说出"没有…"） |
| `expect_extraction=False` 的句子被臆断抽取 | **0**（听不懂不得猜） |

### 5.3 匹配与提醒准确性

| 指标 | 目标 |
| --- | --- |
| Top-3 召回率（真值在候选内） | ≥ 85% |
| Top-1 命中率（`clear` 组） | ≥ 75% |
| Top-1 命中率（`vague` 组，允许落 Top-3） | ≥ 30% |
| `immediate` 组触发「立即就医」 | **100%** |
| `elective` 组误触急症提醒 | ≤ 2% |
| 每条匹配结论都有命中/缺失/排除证据 | 100% |
| 匹配度与参考概率口径一致（只出现这两种说法） | 100% |

### 5.4 稳定性

| 指标 | 目标 |
| --- | --- |
| 连续 500 次请求错误率 | ≤ 0.5% |
| 50 并发下 P95 时延 | ≤ 3× 串行 P95 |
| 2 小时长稳内存增长 | ≤ 10% |
| Celery 队列积压 | 任务结束后 5 分钟内清空 |
| 异常输入下 5xx | 0（应为 4xx 或降级） |
| 越权访问被拒 | 100% |

### 5.5 合规

| 指标 | 目标 |
| --- | --- |
| 红线术语命中 | 0 |
| AI 输出诊断结论 | 0 |
| 缺免责声明的输出 | 0 |
| 关键操作缺留痕 | 0 |

> 任一「红线类」指标不达标即判**不通过**，不接受以「其他指标好」抵扣。

## 6. 执行步骤

1. **准备**（约 30 min）
   - 建独立测试库 `cga_test`；导入 `docs/structured/assessment-scales/` 与疾病库
   - 启动后端 + 前端 + Redis + Celery；确认 `GET /health` 正常
   - `python tools/check_simulated_patients.py` 通过后方可开跑
2. **数据导入**（约 20 min）
   - 用 `tools/gen_simulated_patients.py` 的产物建 100 名患者档案 + 预问诊 + 对话会话
   - 导入脚本（待写）：`tools/seed_simulated_patients.py`
3. **E2E 串行**（约 2 h）：先跑通 1 人全流程，再批量 100 人
4. **准确性核对**（约 1 h）：跑 §5.2 / §5.3 的断言脚本（待写）：`tools/eval_matching_accuracy.py`
5. **稳定性**（约 3 h）：并发梯度 + 2 小时长稳 + 异常注入
6. **出报告**：写进 `docs/review/`，格式参考 `docs/review/` 现有报告

## 7. 风险与前置条件

| 风险 | 应对 |
| --- | --- |
| 大模型不稳定，拖慢并放大时延抖动 | 记录模型版本与提示词版本；把大模型调用单独统计，不与规则引擎时延混算 |
| 测试库被误当生产库 | 独立库 + 独立连接串 + 启动时校验库名，不匹配直接退出 |
| 100 人 × 18 步的 token 成本 | 统一用测试账号的模型配额；对话回放不重复调用（命中缓存或落库复用） |
| 病种真值与匹配引擎口径不一致导致 Top-1 偏低 | 先用 `clear` 组校准；确认是引擎问题还是数据问题，再谈指标 |
| 与线 A 并行开发导致接口漂移 | 跑测前记录双方 commit；接口变更走 `docs/plan/` 契约清单 |
