## 3. 三个真实缺口（按杠杆排序）

### 3.1 M1 出口没达成，而且 `docker compose up` 是假的

`docker-compose.yml` 写好了，看起来基座完成了一半。实际两处硬伤：

1. **`frontend/Dockerfile` 不存在** → compose 在 build 阶段直接失败；
2. **`backend/requirements.txt` 没有 `psycopg`** → 即使前端镜像补上，后端连 PostgreSQL 时
   `sqlalchemy.create_engine("postgresql+psycopg://...")` 会因缺驱动报错。

也就是说，**「一条命令起全栈」这个 M1 出口从未被验证过**，它只是看起来像完成了。
这类「配置写了但没跑过」的假完成，比没写更危险——它会让站会上「基座已就绪」的结论站不住。

### 3.2 407 个测试，但没人自动跑

测试数量是这半个月最扎实的资产（246 → 314 → 407），可它们只在本地手动执行。
没有 CI 意味着：PR 合并前没有人知道有没有破；线上回归只能靠人记得跑。
**这是当前投入产出比最高的一件事**——三条 workflow 就能把已有资产变成门禁。

### 3.3 质量没有数字

`quality_metrics()` 已经能算计分一致率、提醒响应率、匹配 Top 分数与 Gap，
但**没有标注集，就没有准确率**；没有准确率，「匹配准不准」只能靠感觉。
这一项还连带阻塞阈值校准（2.1.2）与自动提醒开关（1.1.3）。

### 3.4 评审卡在「人」，不在「系统」

系统侧该做的都做了：凭据分级、签字人与录入人分离、批量审批、版本化台账、一键落库。
剩下唯一动作是拿到签字人姓名与职称，跑一条命令。
**这件事拖一天，自动触发就一天不能开**，且它是 M2/M3 的共同前提。

## 4. 技术路线（四阶段，重排期）

原排期 M1（11/11~11/22）已过期 3 天且未达成，M2 窗口（11/23~12/06）已开但前置未满足。
按「基座 → 量化 → 闭环 → 发布」重排，每阶段只留一个可验证出口：

| 阶段 | 窗口 | 主题 | 出口（可验证，不含形容词） |
| --- | --- | --- | --- |
| **S1** | 11/25 ~ 12/01 | 工程可交付 | `docker compose up` 起全栈；PR 触发三条 CI 且全绿；`alembic upgrade head` 与 `downgrade` 均可跑；契约漂移时 CI 红灯 |
| **S2** | 12/02 ~ 12/13 | 质量可量化 | 标注集 ≥200 条入库；`eval_matching_accuracy.py` 出 Top-1/Top-3/误报率；时序表建成并接报告趋势 |
| **S3** | 12/14 ~ 12/24 | AI 可运营 | 模型健康指标可见（空回复率/降级率/耗时分位）；提示词可在页面发布回滚；导出脱敏 + HMAC 检索 + 审计补齐 |
| **S4** | 12/25 ~ 12/31 | 发布收口 | `main` 与 `dev` 同步；版本快照可回滚；全量回归绿；文档与代码一致 |

### 4.1 为什么是这个顺序

- **S1 不可跳**：S2/S3 的一切都要靠 CI 兜回归。先做量化再补 CI，等于用没有安全网的方式改核心算法。
- **迁移要在 S2 前完成**：S2 要加时序表、S3 要改 `patients` 加 HMAC 列。现在 27 张表靠
  `_sync_missing_columns()` 手工 `ALTER`，加表越多，补迁移的成本越高，且历史数据无从追溯。
- **S2 与 S3 可分叉并行**：S2 偏数据与算法（标注、校准、时序），S3 偏基础设施与可观测
  （模型指标、提示词 UI、脱敏），两条线互不阻塞，可由两人分头推。
- **S4 只做收口，不接新功能**：12/25 之后任何新需求一律进「二期后」。

### 4.2 关键路径

```
医学评审（人）──→ 开「立即就医」自动触发 ──→ 误报率有意义 ──→ 可对外演示
      ↑ 唯一不在我们手里的依赖
CI + 迁移 ──→ 标注集/校准可安全迭代 ──→ 准确率达标
      ↑ 本周必须落地，否则 S2 全程裸奔
```
