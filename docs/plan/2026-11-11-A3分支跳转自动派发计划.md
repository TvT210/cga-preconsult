## 1. 现象与根因

计划里写的是「分支跳转未自动派发」。排查后确认：**判定逻辑早就有了，缺的是「判定之后那一步」**。

| 环节 | 现状（改造前） |
| --- | --- |
| 题库 | 21 张量表里 21 张定义了 `branches`，共 28 条边 |
| 判读引擎 | `scoring.branch_recommendations()` 在 `finish` 时逐条求值，命中即返回 |
| 接口 | `POST /assessments/{id}/finish` 返回 `branches: [...]` |
| 前端 | 结果页把 `branches` 渲染成一串**纯文本**：「B.3 · 平地行走不能独立…」 |

也就是说，系统会告诉老人「建议加做 SPPB」，但**不会真的把这份量表变成一条可进入的任务**。老人要走回首页、自己在量表列表里翻到 SPPB、再点开始——中间任何一步都可能流失。这是「建议」与「派发」的差别，也是 A-3 要补的唯一一环。

## 2. 关键发现：分支图是成环的

动手前先把 28 条边导出来做了环检测，结果直接影响设计：

| 回指关系 | 说明 |
| --- | --- |
| B.1 ⇄ B.3 | 巴氏指数行走项低分 → 做 SPPB；SPPB 步速 ≤2 分 → 回到巴氏指数 |
| B.4 ⇄ B.5 | 抑郁与焦虑量表互推 |
| B.6 ⇄ B.7 | 睡眠与疲乏互推 |
| B.14 ⇄ B.15 | 跌倒与跌倒效能互推 |
| B.8 ⇄ B.21 | 认知与谵妄互推 |
| B.18 ⇄ B.19 | 吞咽与营养互推 |

DFS 遍历下能枚举出 **80+ 条环路路径**。这不是题库写错——临床上「A 异常要进一步看 B，B 异常也提示回头看 A」本来就合理。但这意味着**自动派发如果没有环路防护，一次阳性会无限派生任务**，患者列表会被同一批量表刷屏。

结论：环防护不是可选项，是 A-3 的前置条件。

## 3. 设计

### 3.1 红线

1. **只派任务，不代填、不下结论。** 派生出来的是 `in_progress` 空壳会话，与患者手动新建的任务完全等价；派发不改变任何量表的分级，也不会因分支命中就生成结论。
2. **是否加做由患者和医护决定。** 系统只把「该做的事」摆到眼前，不替人做决定。
3. **不派空量表。** 条目未按标准原文补录的量表不可采集，跳过并说明原因，而不是给出一个点进去就报错的入口。

### 3.2 环防护怎么落地

给会话加一条溯源边：

```
AssessmentSession.dispatched_from_id  → 触发它的那次会话
AssessmentSession.dispatch_branch_code → 是哪条分支触发的
```

沿着 `dispatched_from_id` 向上回溯，就得到「本次评估链」上出现过的量表集合。目标量表只要在这个集合里，就判为 `skipped / cycle`。

选择「按链」而不是「按患者历史」的理由：患者三个月前做过 SPPB，不代表这次不能再做。链只覆盖**同一次筛查派生出来的路径**，语义正好。

回溯设 `MAX_CHAIN_DEPTH = 12` 上限，兜住历史脏数据造成的超长链。

### 3.3 四种去重

| 情形 | 处理 | `status` / `skip_reason` |
| --- | --- | --- |
| 目标已在本次链上 | 不派 | `skipped` / `cycle` |
| 同一批分支重复指向同一量表 | 只派一次 | `skipped` / `duplicate` |
| 患者已有该量表进行中任务 | 复用，不新建 | `reused` |
| 同一会话重复 `finish` | 返回首次结果，不重复建 | `reused` |
| 量表条目未补录 | 不派 | `skipped` / `no_questions` |
| 题库无此量表 | 不派 | `skipped` / `scale_missing` |

## 4. 实现

| 文件 | 改动 |
| --- | --- |
| `backend/app/db/models.py` | `AssessmentSession` 增 `dispatched_from_id`（自引用 FK）、`dispatch_branch_code` |
| `backend/app/services/branch_dispatch.py` | 新增。`chain_scale_codes()` 链回溯 + `dispatch_branches()` 派发 |
| `backend/app/api/assessments.py` | `finish` 接入派发，响应新增 `dispatched`，审计记录派发条数 |
| `frontend/src/lib/types.ts` | 新增 `DispatchedBranch`，`AssessmentFinishResult` 增 `dispatched?` |
| `frontend/src/app/elder/scale/[id]/page.tsx` | 结果页「建议追加的评估」改为带入口的卡片 |
| `backend/tests/test_branch_dispatch.py` | 新增 6 条用例 |

### 数据库升级

项目尚未引入 Alembic，沿用 `init_db._sync_missing_columns()` 的轻量迁移：`create_all` 后比对模型与实际列，缺失的 `ALTER TABLE ADD COLUMN` 补上。已验证既有库可平滑升级（新列出现在 `assessment_sessions` 上）。注意该机制不补外键约束，SQLite 下不影响使用。

### 前端为什么不用传 `session_id`

`elder/scale/[id]/page.tsx` 原本就是「先查该患者 + 该量表的 `in_progress` 会话，没有才新建」。派发已经把任务建好，所以从结果页跳到 `/elder/scale/B.3` 会自动接上那条任务，前端只需一个链接。这也是不在 URL 上带会话 id 的原因：断点续填的既有语义已经覆盖。

## 5. 契约变更（CA-20261111-02）

`POST /assessments/{id}/finish` 响应新增 `dispatched: DispatchedBranch[]`。

- `branches` **原样保留**，语义不变（建议列表）；
- `dispatched` 是建议的落库结果，字段见 `docs/api-contract.md`；
- 纯新增字段，B 线不读也不受影响。
