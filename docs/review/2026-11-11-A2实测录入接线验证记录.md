## 2. 改动的三个断点（逐个验证）

### 断点 1：`measure.unit` → `unit` 字段展开

新增 `backend/app/services/scale_presenter.py`，`GET /scales/{code}` 与 `GET /assessments/{id}` 的题目统一经其展开。

实测结果（`GET /scales/B.3`）：

```
B3-01 | unit= s | banded= True | fallback= ['no_try']
B3-04 | unit= s | banded= True | fallback= ['unable']
```

验证原则写在测试里：

- `test_presenter_does_not_mutate_source_scale`：`get_scale()` 回退到 JSON 基线时返回的是**缓存中的同一个字典**，若就地改写会污染全进程的题库。presenter 用深拷贝，测试比对改写前后的 JSON 快照。
- `test_presenter_is_idempotent`：重复调用结果不变，避免二次展开产生 `unit_hint` 漂移。

### 断点 2：实测分档题（`input_type=single`）走不到数字输入

这是计划里最容易被低估的一点。全库 10 道 `measure` 题中，**8 道是 `single` 型**——临床上要「测秒数→落档」，但题库把它们表达为「带 min/max 区间的单选选项」。前端原先只在 `input_type === "number"` 时渲染输入框，所以这 8 道题永远只能手点档位。

服务端新增 `banded_input` 标记（`input_type=="single"` 且存在带区间的选项），前端据此渲染「数值输入 + 计时器 + 兜底选项」。

分类边界由测试钉住：

| 题目 | `banded_input` | 理由 |
| --- | --- | --- |
| B3-01~B3-05、B17-01、B7-01/02 | `true` | 单选 + 选项带数值区间 |
| B12-01、B12-02 | `false` | `number` 型纯记录项，无区间可落 |
| B1-01 等普通单选题 | `false` | 无 `measure`，不得误判为实测项 |

`fallback_options` 的语义通过洼田试验验证：`B17-01` 的 6 个选项中只有「1 级 ≤5 s」「1 级 >5 s」带区间，其余 2~5 级靠表现定档 → `fallback_options == ["l2","l3","l4","l5"]`，前端渲染为独立按钮。

### 断点 3：只填实测值被前端拦为「未作答」

`elder/scale/[id]/page.tsx` 原校验 `entry.value` 非空才放行，而实测分档题的正确提交是 `value=null, measured=4.5`。已抽出 `isAnswered()`：`measured` 有值即视为已作答；`handlePause` 同步修正，避免暂停时丢实测值。

## 3. 实测值全链路（接口级验证）

| 场景 | 请求 | 结果 |
| --- | --- | --- |
| 只填秒数（SPPB 步速） | `{"question_code":"B3-04","measured":4.5}` | `value=lt_4_82`、`score=4` |
| 只填秒数（洼田） | `{"question_code":"B17-01","measured":4.5}` | `value=l1_within5`、`score=1` |
| 改选兜底选项 | `{"question_code":"B3-04","value":"unable"}` | `value=unable`、`score=0` |
| 数值超出所有区间 | `measured=9999` | `422`，文案含「分档区间」 |
| 断点续填 | 重新 `GET /assessments/{id}` | `answers[].measured == 5.5`，`value=4_82_6_20` |

最后一项是本轮顺带修掉的缺陷：`_session_payload` 的 `answers` 数组原先**没有返回 `measured`**，导致刷新后实测值丢失、只剩归档档位。补上后，老人重新进入评估页能看到上次测的秒数。

## 4. 领域红线自查

| 红线 | 落实方式 |
| --- | --- |
| 阈值外置，不写死在代码 | 前端预演落档用的是题库 `options[].min/max`；真正定档仍在后端 `_band_for`，改题库即生效 |
| AI 不输出诊断 | 表述统一为「将记为：<档位>」「需人工确认」，无「诊断」字样 |
| 缺项/矛盾不静默 | 数值与档位矛盾仍记 `measured:band_check` 并置 `needs_manual_review`（既有行为未改） |
| 结论可回溯 | 结果页对实测题显示「实测 4.5 秒（<4.82 秒）」，而不是把 4.5 误显示成分值 |

**一处主动的设计约束**：前端不做「值 → 档位」的终局判定，只做即时预演。若两边逻辑漂移，以服务端为准，且前端会把不在任何区间的数值明确提示「请核对或与医护人员确认」，不会静默落档。

## 5. `next build` 未能执行的原因（环境，不是代码）

三次尝试均在 Next 写 `.next/trace` 时报 `EPERM: operation not permitted`，换 `distDir` 后同样位置报错，排除项目路径问题。另有 `rm -rf .next` 触发宿主「批量删除确认」（79 个文件 > 阈值 50）。

已验证的替代手段：

- `npx tsc --noEmit` → 0 error（类型层面等价于 `next build` 的类型检查阶段）
- `npx eslint src --max-warnings=0` → 0 告警

**留给你的操作**：`frontend/.next` 目前残留约 129MB 的半成品构建产物（已被 `.gitignore` 忽略，不会提交）。你可以在自己的终端执行 `rm -rf frontend/.next` 清理，再跑 `pnpm build` 确认——我这边受宿主保护无法批量删除。
