## 1. 为什么是这三块，而不是「两个示例用例」

计划里 A-6 写的是「Vitest + RTL，2 个示例用例」。骨架当然要能跑，但如果只为演示跑通，
它护不住任何东西。这一轮正好刚合并 A-3（按 `when` 过滤题目）和 A-7（SSE 流式对话），
两处新代码有一个共同特征：

> **出错不会抛异常，只会静默算错或静默少显示。**

- `lib/conditions.ts` 是后端 `evaluate_conditions` 的第二份实现。两边语义一旦漂移，
  老人看到的题和后端计分的题就不一致——分数照常出，只是错。
- `lib/api.ts` 的 `streamDialogueMessage` 是手写 SSE 帧缓冲状态机。帧被切断、心跳行、
  CRLF、主动中断任一处处理错，表现为「回复少了半句」，日志里什么都没有。

所以首批用例直接压在这两处，外加一个组件用例把「实测值 → 落档」的界面口径钉住。

## 2. 技术选型

| 选择 | 理由 |
| --- | --- |
| **Vitest 3.2** | 与项目已有的 TS / ESM 配置天然兼容，不需要为 Next 项目再配一套 babel；冷启动约 2.3s |
| **jsdom 26** | 组件测试需要 DOM；纯逻辑测试跑在 jsdom 里也无副作用，不为两类测试维护两套环境 |
| **@testing-library/react 16** | React 19 支持；断言方式贴近老人真实操作（按 role / label 找元素），而非查 class |
| **不启用 `globals`** | `describe/it/expect` 显式 `import { ... } from "vitest"`。ESLint 与 tsc 都不需要额外声明，也不会污染生产代码的全局 |

配置只有 `vitest.config.ts` 一个文件：`@/` 别名对齐 `tsconfig.paths`，
`setupFiles` 指向 `src/test/setup.ts`，`restoreMocks: true` 保证 fetch 桩不会跨用例泄漏。

## 3. 用例分布（32 条）

### 3.1 `src/lib/conditions.test.ts`（17 条）

钉住「前端可见题 == 后端计分题」这条不变量。`when` 结构**直接取自题库原文**
（B.15 的 `{all:[{question:"B15-00",op:"eq",value:"vent"}]}`、
B.18 的 `{any:[S1..S4 eq "yes"]}`），题库改动时这里会先失败。

| 关注点 | 断言 |
| --- | --- |
| 阳性判定 | 分值为 0 时即使选了也不算阳性；未作答不抛错、判否 |
| `eq` vs `in` | `eq` 比整值，多选答案（`a,b`）必须用 `in` 才按词条比 |
| 数值比较 | 用**分值**而非选项 value（`ge70` 这类取值只能靠 score 比较）；无分值时一律判否 |
| `any` / `all` | 任一成立 / 全部成立 |
| B.15 分流 | 未插管只出 4 题（含发声题）、插管只出机械通气题；分流题没答时两条分支都不显示 |
| B.18 初筛 | 初筛全否 → 终筛不出现；任一项为「是」→ 终筛展开 |
| `buildFacts` 落分 | 数值题按填入值、实测分档题按档位分值、多选题求和、空数组不算已作答 |
| 区间外 | 落在所有档位之外时 `score = null`，不默认按 0 分处理 |

### 3.2 `src/lib/api.stream.test.ts`（8 条）

| 关注点 | 断言 |
| --- | --- |
| 正常流 | 增量按到达顺序回调；`safety_note` 首帧走 `onSafety`；收尾事件走 `onDone` 不重复走 `onDelta` |
| 帧被切断 | `'data: {"reply":"请稍'` + `'等，"}\n\n'` 能拼回完整帧（缓冲区必须跨 chunk） |
| 代理兼容 | `\r\n\r\n` 分隔、`: ping` 与 `data: keep-alive` 被跳过 |
| 请求形态 | URL、POST、`Accept: text/event-stream`、`Authorization` 来自 localStorage |
| 无收尾事件 | 抛 `ApiError("对话中断…")`，绝不把半截回复当完整结果 |
| HTTP 错误 | 抛后端给的 `message`（如「会话不存在」），不是 `HTTP 404` |
| 主动中断 | fetch 被 abort → 返回 `null` 且不抛错（点「停止」是正常操作） |
| 读流中断 | 已回调的增量保留，整体返回 `null` |

### 3.3 `src/components/QuestionCard.test.tsx`（7 条）

| 关注点 | 断言 |
| --- | --- |
| 实测落档提示 | 填 6.5 秒显示「将记为：需部分帮助（5~15 秒）（本题 1 分）」 |
| 区间外 | 999.5 显示「不在标准给定的任何区间内」，且**不**显示任何档位 |
| 数值输入 | 受控回写后 `onChange(null, 12)` |
| 兜底选项互斥 | 点「不能完成」时 `measured` 传 `undefined`，清空实测值 |
| 单选 / 多选 | 单选返回选项 value；多选在已选基础上追加、再点取消 |
| 代答标记 | `isProxy` 时渲染「家属代答」 |

## 4. 刻意没做的

1. **没有覆盖率门槛**。现在盖的是关键路径，不是全量代码；先设门槛只会逼人写凑数的测试。
   等 B-2 的 CI 跑起来、用例铺开后再定阈值。
2. **没有测 401 跳转**。该分支会写 `window.location.href`，jsdom 会报
   「Not implemented: navigation」，测出来的失败点与真实行为无关，反而误导。留给 e2e。
3. **没有配 CI**。仓库当前无 `.github/workflows`，这项归线 B 的 **B-2**（`frontend.yml`）。
   本轮的交付边界是「命令可用」：`pnpm test` 一条命令即可接入。
4. **没有引入快照测试**。快照只会随界面改版一起漂，对这类适老化界面没有约束力。

## 6. 使用约定（已写入 `frontend/AGENT.md` 第 14 条）

- 测试文件与被测代码同目录：`src/lib/xxx.test.ts`、`src/components/Xxx.test.tsx`
- **改 `conditions.ts` 或后端 `evaluate_conditions` 任一侧，都要跑 `conditions.test.ts`**
- **新增纯逻辑 / 状态机，一并补测试**——这类代码出错不报异常，只会静默算错
- `pnpm test` 跑一次即退出，`pnpm test:watch` 为监听模式
