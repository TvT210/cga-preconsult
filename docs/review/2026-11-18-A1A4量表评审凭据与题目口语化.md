# A-1 / A-4 完成记录：量表评审凭据与题目口语化

> 2026-11-18 ｜ 线 A（采集与判读）｜ 契约 CA-20261118-02、CA-20261118-03

## 1. 起点核对：计划表写的和实际差的不是一点

计划表把 A-1 写成「21 张量表医护逐张评审，`review_status` → `approved`」，读代码后发现三处比「点 21 次按钮」更靠前的问题：

| # | 问题 | 后果 |
| --- | --- | --- |
| 1 | `PUT /scales/{code}/review` **忽略**了前端传来的 `reviewer`，硬编码取当前登录账号名 | 外部专家没有系统账号，代录之后审批记录里写的是同事的名字——不是格式问题，是把没发生的事记成发生过的 |
| 2 | `get_scale()` 用 `setdefault("review_status", …)` 取评审态，而题库 JSON 里本来就写着 `draft_pending_medical_review` | 数据库改成 `approved` 后判读读到的仍是 draft，表现为「评审完结论还说待评审」。**不修这条，A-1 做了等于没做** |
| 3 | 只能逐张点，21 张要点 21 次，且没有「谁签的、凭什么签」的记录 | 评审结论无法审计，也无法回答「这批量表凭什么放行」 |

A-4 同样：题库里 127 道题的 `plain_text` **已经全覆盖**（上一轮做题库时写好），缺的是「改写接口 + 审批回写」这条链路——也就是说 A-4 的产出不是文案，是**能力**。

## 2. 做了什么

### 2.1 签字人与录入人分开记

```
template_approvals
  reviewer        谁签的字（人，可能不在系统里）
  reviewer_title  职称/科室
  evidence_type   signed_document | in_system | verbal_confirmation
  operator        谁把这条记录录进系统
  reviewed_at     签字日期（可与录入时间不同）
```

`scale_templates` 同步保存 `reviewer_name / reviewer_title / review_evidence / reviewed_at`，供列表与判读直接读取。

校验统一收在 `scale_review.validate_evidence()`，量表评审与文案回写共用：

- `evidence_type` 必填；
- `reviewer` 必填（`in_system` 时自动取当前账号）；
- `approved` 必须有职称与签字日期；
- `verbal_confirmation` 必须写依据。

### 2.2 批量评审

`POST /scales/reviews/batch`，要求显式传 `codes`，**不提供「默认全部」**。逐张落库，一张失败不影响其余；信息与上次完全一致时返回 `unchanged`，不重复写记录。

### 2.3 评审结论可版本化

评审状态原本只存在数据库里，换一台机器部署就没了。新增台账 `docs/structured/scale-approvals.json`，`init_db()` 启动时应用：

- 只对**仍为草稿**的量表应用，已有人工后续决定（如 `deprecated`）不覆盖；
- `reviewer` 为空的条目**跳过**——宁可仍是草稿，也不写一条查不到责任人的审批记录；
- 按「量表 + 结论 + 签字人 + 凭据」去重，重复启动不堆记录。

### 2.4 判读提示按凭据分级

`approved` 不再等于「已签字」。凭据为口头/线上确认时，判读仍标 `needs_manual_review=true`，但提示语换成：

> 本题库评审凭据为「口头/线上确认」，签字件待补；结论可用于随访参考，正式出具前需医护确认

原来那条「题库待评审，结论仅供演示」则不再出现——它已经过评审，只是凭据不足。

### 2.5 A-4：改写只进候选池

| 接口 | 作用 |
| --- | --- |
| `POST /scales/{code}/plain-text/draft` | 生成候选，**不改动**已评审的 `plain_text`，只写进 `payload.plain_text_draft` |
| `POST /scales/{code}/plain-text/apply` | 审批后提升为 `plain_text`，留 `scale_versions` 与 `template_approvals(target_type="scale_plain_text")` |

三条护栏在 `plain_text.guard()`：

1. **症状词增减**：候选引入了原题干没有的症状词（或漏掉原有的）→ `apply` 时拒绝；
2. 长度（4~120 字）、换行、英文词 → 提示但不拦；
3. 只碰 `plain_text`，`code` / `options` / `score` / `when` / `measure` 一律不动。

mock 环境走规则改写（确定性输出，离线可用），接入真模型时走提示词；两种情况都必须过 `apply` 审批。

### 2.6 前端

- `components/ReviewEvidenceFields.tsx`：凭据表单唯一实现，配置页与口语化页面共用；
- `/staff/config`：五字段表单 + 凭据类型说明 + 口头确认的后果提示 + 勾选批量审批 + 表格显示「谁签的、什么凭据、是否无签字件」；
- `/staff/plain-text`（新页）：选量表 → 勾题 → 生成候选 → 逐条可改 → 审批回写，风险提示直接列在候选下。

## 3. 21 张量表的落库方式

评审结论写入 `docs/structured/scale-approvals.json`（21 条），内容为：结论 `approved`、凭据 `verbal_confirmation`、签字人、签字日期与依据说明。该文件随代码走，新环境部署后自动应用。

## 5. 刻意没做的

1. **不把口头确认写成签字件**。判读仍标需人工确认，见 §2.4。
2. **不做「评审附件上传」**。签字件目前没有实体文件，加个上传入口只会放一个空目录。
3. **不改题库 JSON 里的 `review_status`**。题库原文与评审结论分离，改基线会让「题库是什么」和「谁批准的」两件事混在一起。
4. **不做 AI 自动审批**。改写产出必须人来批，护栏只负责把可疑项推到人眼前。
5. **不动 `total_questions`**。仍是全量题数，牵动质控指标，属既有遗留。

## 6. 遗留

- 量表题库存量更新不会同步到已有数据库（`seed_scales` 只在行不存在时写入 payload），需另开一轮处理；
- 台账只记录 `scale` 与 `scale_plain_text` 两类，疾病库与阈值仍走各自接口；
- 若后续拿到签字件，改 `evidence_type` 为 `signed_document` 并补 `comment`（原件位置），判读提示会自动消失。
